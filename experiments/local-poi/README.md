# Локальний транспортний каталог POI — ізольований прототип

Пошук працює без мережі, з окремим `data/poi.sqlite` лише для читання.
Чинні frontend, Kotlin backend, PostgreSQL, PRG SQLite та `/addresses/search` не змінюються.
Прототип не запускає серверів, імпорту у робочі бази або фонових оновлень.
Результати й обмеження — у [REPORT.md](REPORT.md).

## Спробувати

З кореня репозиторію, без сторонніх Python-бібліотек для самого пошуку:

```bash
python3 experiments/local-poi/search.py ork
python3 experiments/local-poi/search.py 'szpital kliniczny nr 4'
python3 experiments/local-poi/search.py 'Teatr w Budowie'
python3 experiments/local-poi/search.py 'pzl swidnik'
python3 experiments/local-poi/demo.py ork --prg experiments/local-geocoder/data/addresses.sqlite
```

Очікування: `ork` повертає Galeria Orkana. Demo показує окремі групи зупинок,
незмінених PRG-адрес і POI, у такому порядку; серед адрес є Władysława Orkana.
PRG зберігає свій наявний порядок: першою може бути Orkiszowa. Ніякого глобального
обрізання, яке витісняє адреси або зупинки, demo не робить. Це приклад контракту,
а не зміна дизайну/лімітів чинного планувальника.

`arrival_lat/lon=null`, `arrival_status=unresolved` — надійних входів у використаних
даних не встановлено. `lat/lon` є координатами об'єкта; не приймайте їх за перевірений
вхід або гарантовано доступну точку пішохідного прибуття.

## Файли

- `rules.py` — критерії призначення, явні винятки та умовні ваги категорій.
- `overrides.json` — переглянуті конфлікти конкретних вихідних записів.
- `audit-overrides.json`, `curation.py` — погоджені рішення аудиту: точний source/ID, очікувана джерельна назва, причина, канонічна назва та ідентифікатор конкретного майданчика. Зміна очікуваної назви зупиняє побудову для повторного перегляду.
- `verify_rebuild.py` — незалежна повторна побудова в тимчасовому каталозі та порівняння SHA256 SQLite, рішень і прапорців.
- `evidence.json` — офіційні підтвердження призначення окремих підприємств.
- `sources.json` — точні джерела, SHA256, просторовий відбір та ліцензійні артефакти.
- `prepare.py` — перевірка/копіювання вже отриманих вихідних файлів.
- `build.py` — детермінована офлайн-побудова. `search.py` — пошук.
- `test_poi.py`, `benchmark.py` — перевірки та вимірювання.
- `data/decisions.jsonl` — рішення щодо кожного перевіреного названого кандидата.
- `data/review.json` — включені POI з прапорцями якості та вихідними ID.
- `data/catalog.csv` — список відібраних місць для ручного перегляду.
- `data/search-examples.json`, `mixed-ork.json`, `*-metrics.json` — фактичні результати.
- `data/cleanup-comparison.json` — зафіксоване порівняння з початковими 390 POI:
  SHA256 старої бази, збережені джерела, вилучення та 10 розділених груп.
  Архівуйте цей файл разом із результатами аудиту: він потрібен для повторного
  експорту звіту `report.py`, але не для побудови SQLite чи перевірки її повторюваності.

Дані та SQLite виключені з Git. Для перенесення/архівування зберігайте `data/sources/`
разом із кодом, `sources.json` і `licenses/`; `/tmp` для повторної побудови не потрібен.

addresses, websites, version. Це просторова вибірка з двох файлів релізу,

Оригінальне хмарне розміщення та SHA256 локального Parquet — у `sources.json`.

BDOT10k: лише локальні повітові пакети **0663 (Lublin) та 0617 (Świdnik)**,
схема 2021. Поза цими двома пакетами BDOT не перевірено. З них читаються
іменовані комплекси та будівлі, а не всі дороги, комунікації та зупинки.
Весь повіт Świdnik не включається автоматично: діє фільтр тих самих 16 ґмін.
Новий пакет 0617 — близько 34 MB; 0663 використано з попереднього дослідження.

Wikidata: **три підтверджені сутності**, Q24121676, Q1916610, Q9186420,
із точними ревізіями. Це точкове збагачення назвами, не повний зріз Wikidata.
Попереднє масовіше читання отримувало HTTP 429; жодних припущень про повноту.

GTFS: локальний статичний знімок із дослідження PRG від 07.11.2026.
З нього обчислюється найближча точка зупинки по прямій; частота руху, актуальність
обслуговування та пішохідна досяжність цим **не** доводяться.

## Повторна побудова

Лише для побудови й географічних тестів потрібні пакети з `requirements-build.txt`.
Встановлюйте їх у власне venv; пошук їх не імпортує.

```bash
python3 -m venv /tmp/lubus-poi-venv
/tmp/lubus-poi-venv/bin/pip install -r experiments/local-poi/requirements-build.txt
/tmp/lubus-poi-venv/bin/python experiments/local-poi/prepare.py --cache experiments/local-poi/data/sources
/tmp/lubus-poi-venv/bin/python experiments/local-poi/build.py
/tmp/lubus-poi-venv/bin/python -m unittest discover -s experiments/local-poi -p 'test_*.py' -v
python3 experiments/local-poi/benchmark.py
```

Під час цієї роботи бібліотеки вже були локально доступні в дослідницьких `/tmp/.../lib`;
саме ці версії зафіксовані у requirements. Мережа потрібна лише для встановлення
бібліотек або свідомого отримання нових даних. `prepare/build/search` самі нічого не качають.

`prepare.py --cache /шлях/до/архіву` дозволяє відновити локальний кеш із архівованих
файлів. Побудова перевіряє всі SHA256 та тексти ліцензій/NOTICE й відмовляється працювати
з підміненим входом. Нову базу спочатку створює як `.building`, перевіряє, потім замінює
**лише власний вихідний файл**. Невдала побудова не перезаписує готовий каталог.
Не запускайте одночасно дві побудови в той самий output.

Для нового знімка: отримайте локальну вибірку Overture за тим самим bbox з полями,
переліченими вище, актуальні потрібні повітові BDOT ZIP та вибрані Wikidata-сутності;
зафіксуйте нові версії, файли, SHA256, умови й дату у `sources.json` та кешовому
`manifest.json`, перегляньте правила/винятки, перебудуйте й перевірте зміни кількості.
Повітові ZIP та API Wikidata можуть змінюватися за тим самим URL: точне відтворення
старого каталогу гарантоване лише з архівованим перевіреним кешем.

## Відбір

Немає квоти на загальну кількість. `include/review/reject` означають відповідно:
кандидат у прототипі, недостатньо доказів для включення, поза погодженим призначенням.
`review` не показується в пошуку. Для нього зберігається причина, а сирий запис
залишається в перевіреному джерелі.

Основне правило — категорія плюс назва, яка підтверджує фізичне призначення.
Професійні/торгові послуги, орендарі галерей, приватні кабінети, заходи, навчальні
підрозділи й дрібний бізнес не проходять лише через категорію джерела.
Переглянуті винятки дозволяють включити Lublin Plaza, Targi Lublin, Aqua Lublin,
Hala Globus та підприємства навіть за помилкової категорії.

Промислові об'єкти: перевірені названі кандидати Overture; для BDOT — названий
виробничий/сервісний комплекс **від 1 ha** з виключенням явно торгових/автосервісних
об'єктів. Площа є фізичним сигналом масштабу, не оцінкою робочих місць або змінності.
Для спортивних територій BDOT використано поріг 0,5 ha; явно визначені великі
спортивні заклади Overture проходять незалежно від наявності полігона.
Пороги не обмежують загальну кількість і задокументовані для перегляду.
Сільські звичайні школи не включаються масово; ліцеї, технікуми, університети
та шкільні комплекси є регулярними пунктами поїздок.

`permanently_closed` Overture виключається. Низький confidence лише додає прапорець.
Стара версія BDOT, невідомий статус роботи, конфлікти координат зберігаються як
ознаки для перевірки. Існування запису не є підтвердженням роботи об'єкта сьогодні.

Об'єднання підприємств, лікарень та освітніх закладів потребує підтвердження
того самого фізичного майданчика: явного `site` у винятках аудиту (до 250 м)
або однойменної точки/будівлі всередині території. Однакова назва чи бренд і
навіть близькі координати самі по собі не є підставою для злиття.
Різні явні `site` не зливаються, зокрема через проміжну невизначену територію.
Для решти категорій: близька назва й до 80 м, парки — 350 м,
контрольні ідентичності VIVO/CSK — 200 м, аеропорт — 1500 м.
Збереження окремих записів за браком доказів може залишати дублікати;
такі пари потребують ручного підтвердження фізичного місця.

28 BDOT-будівель із загальною назвою університету та невизначеним типом
отримують явне `education/review/campus_component_requires_site_review`.
Вони не потрапляють у пошук автоматично. Уже включені будівлі з визначеним
типом BDOT цим правилом не вилучаються. Точкові винятки аудиту не послаблюють
загальні фільтри; неактивний BDOT-об'єкт і permanently_closed Overture
не обходять перевірку стану через виняток.

Перевірка після побудови (з установленими build-залежностями):

```bash
python3 -B experiments/local-poi/build.py
python3 -B -m unittest discover -s experiments/local-poi -p test_poi.py -v
python3 -B experiments/local-poi/verify_rebuild.py
python3 -B experiments/local-poi/benchmark.py
python3 -B experiments/local-poi/report.py
```

Усі вихідні варіанти назви, геометрії й походження залишаються в `features`.
Якщо точка Overture поза відповідною територією BDOT, для нетранспортного POI
використовується внутрішня точка території з явним прапорцем конфлікту. Це
представлення об'єкта, не розв'язання питання входу. Кампуси/корпуси, що лишаються
окремими, потребують уточнення назв/контексту перед продуктовою інтеграцією.

## Пошук і ранжування

Окремі таблиці `pois`, `features`, `provenance`, `names`, `entrances`, `metadata`.
FTS5 містить нормалізовані назви, prefix-індекси 2/3/4; польські діакритики й `ł`
зводяться до ASCII. Усі слова запиту мають збігатися за початком слова в одній назві;
порядок слів може відрізнятися. Число у `nr 4` не розбирається як номер будинку.

Порядок: точна назва → початок назви → префікси окремих слів. При однаковій
текстовій відповідності канонічна назва перед alias, далі умовна вага призначення,
відстань до найближчої зупинки, назва й ID для стабільності. Ваги категорій —
продуктова евристика, не вигадана популярність/пасажиропотік.

Runtime: стандартний Python + SQLite, нове read-only з'єднання на запит, page cache
2 MiB, SQL-обмеження результатів 1..50. Весь каталог у Python/RAM не читається.
SQL ранжує всі текстові збіги до LIMIT; довільної попередньої квоти кандидатів немає.
Побудова разова й пам'яттєво важча за пошук; її RAM вимірюється окремо.

## Для майбутньої інтеграції

Потрібні окремий read-only сервіс пошуку POI, підтримка `type=poi` у контракті та
картках, ізоляція відмов PRG/POI й погоджені квоти змішаних результатів. Зупинки
мають залишатися першими; адресний збіг із номером не можна витісняти POI.
Зберегти ліцензії/NOTICE, ID/походження та сторінку джерел.

До підключення маршрутизації потрібно перевірити конфліктні точки, відрізнити
автобусний Dworzec Lublin від Lublin Główny, уточнити кампуси й незалежні корпуси,
визначити входи/прохідні. `entrances` порожня, arrival NULL: маршрутизатор не повинен
мовчки називати репрезентативну точку перевіреним входом. Зв'язки із пішохідним
графом і версією графа варто тримати окремо.

Ліцензійні подробиці й збережені документи — [licenses/README.md](licenses/README.md).

## Фінальне очищення пошукових представлень

`presentation-rules.json` фіксує source/ID членів десяти перевірених груп.
Групи 1–3 об'єднуються канонічно, з усіма `features` і `provenance`.
Групи 4–10 зберігають окремі фізичні місця. У групах 4 і 6 назви уточнені
достовірними функціями BDOT (лікарняна будівля, освітня територія, бібліотека).
У групах 5, 7, 8, 9, 10 другий запис тимчасово прихований.
Таблиця `search_presentations` містить visible, representative_id і причину;
пошук повертає лише visible=1. Приховані місця та їхні назви не видаляються.
Перший представник визначений порядком погодженого аудиту, а не популярністю.
`catalog.csv` експортує також видимість, щоб не плутати фізичні місця з підказками.
`data/final-preservation.json` фіксує порівняння всіх 542 вихідних записів
із попередньою базою 414 POI; поточні кількості й вимірювання — REPORT.md.

## Відтворювані адреси промислових майданчиків

`address-overrides.json` прив'язує підтверджений поштовий підпис до стабільного POI ID.
Запис містить очікувані назву, координати, source IDs, дату, джерело, URL,
confidence і пояснення. Генератор відмовляється застосовувати запис, якщо склад
джерел або ідентичність місця змінилися. Адреси зберігаються в окремій таблиці
`address_overrides`, не змінюючи features/raw_json/provenance/pois/names.
Kotlin читає confirmed-уточнення перед сирими адресами Overture; старі SQLite
без цієї таблиці зберігають попередню поведінку. API і ранжування не змінено.
Невирішені кандидати — `address-review.json`, усі рішення й питання власнику —
`INDUSTRY_ADDRESS_DECISIONS.md`. Майбутні уточнення власника позначаються
source=local_knowledge з датою й поясненням; внесено 28 уточнень власника.

Після уточнень власника адресні overrides охоплюють усі початкові 54 випадки; 28 записів мають source=local_knowledge. Art-Bet та Art Bed знаходять той самий POI. Нових фізичних майданчиків не створено.
