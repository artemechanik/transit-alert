# Local POI integration

`GET /addresses/search?q=...&limit=...` returns a ranked mixture of PRG streets/addresses
and local POI. `/stops/search` remains independent; the planner renders stops first,
then at most four results from this endpoint. There is no external geocoder fallback.

## Data and startup

Set `POI_SQLITE_PATH` to the existing `experiments/local-poi/data/poi.sqlite`.
Without the variable, the service checks this path relative to the repository root
or backend directory, matching the PRG development convention. The SQLite is ignored
by Git: a fresh checkout needs the archived pinned source cache and build dependencies;
follow `experiments/local-poi/README.md` to build it offline. Never build at server startup.
The current snapshot contains 406 visible presentations / 411 places / 542 source records.

`PoiSearch` is independent of `PrgAddressSearch`: each has its own coroutine semaphore
with four permits. Each query uses a separate mode=ro / query_only JDBC connection,
closes connection/statement/result set with use, and executes on Dispatchers.IO.
POI page cache is 2 MiB per connection, SQL progress budget about 2 seconds after admission.
Only up to 50 ranked rows are returned to Kotlin; the catalog is not loaded into RAM.
No Python subprocess, imports, migrations, SQLite writes or startup database probe.

Docker Compose currently runs PostgreSQL only; no Compose change or restart is needed.
For a future backend container, explicitly mount the POI SQLite read-only and set the
path inside that container. Distribute the pinned licenses/NOTICE alongside the catalog;
source IDs, raw records, versions and per-record licenses remain in its existing tables.
A future data-sources page must follow `experiments/local-poi/licenses/README.md`.
No per-suggestion attribution UI is added in this change.

## Contract and ranking

Existing PRG fields and their meaning remain unchanged. Optional fields `category`,
`subtitle`, `site_id`, `address_line`, `address_status` are absent by default on PRG
responses. POI uses `type=poi`, stable `id`, `display_name`, `lat/lon`, category,
site_id and subtitle. `address_line` is the original Overture freeform postal line;
`locality` is the source locality when unambiguous, otherwise the known gmina.
`address_status` is full / partial / none. Subtitle contains only source address
components, falling back to locality/gmina. It never contains generated coordinates.
No missing street expansion or street-type prefix is invented: Orkana remains Orkana.
Object coordinates remain in lat/lon, **not** a verified walking arrival point.

POI matching and SQL ordering duplicate the Python prototype: normalized Polish letters,
all query tokens as word prefixes, aliases, exact / name-prefix / word-prefix tiers,
canonical-name preference, relevance, nearest stop, stable name/ID. Hidden presentations
are filtered in SQL. No FTS expressions from the raw query enter SQL.

`PlaceRanking` merges two already-ranked streams without reordering either stream:
POI tiers are 0/1/2; PRG exact=0, suffix=1, prefix/word-prefix=2, fuzzy=3.
Address results get a one-level bonus, protecting concrete address matches. On equal
levels streams alternate, starting with POI; this avoids starvation without hard source
quotas. The public limit applies after mixing (frontend requests four). A weak POI cannot
jump ahead of a stronger PRG head. The original PRG algorithm and SQL are unchanged.

Each dictionary may fail independently: the surviving results are returned with warning;
if both fail, a nonempty search gets 503. Empty input still returns an empty 200 response.
Invalid parameters remain 400. POI names containing numbers use their whole query,
independently of PRG house-number parsing (e.g. `7r`, `szpital kliniczny nr 4`).
Status, stops and other routes do not depend on either dictionary.

## Validation

Run `cd backend && ./gradlew test`; frontend: `node --experimental-vm-modules --test frontend/tests/*.test.mjs`.
`PrgAddressSearchTest` explicitly disables POI for its 58 full-response Python parity
scenarios; it verifies the same PRG-only route contract and concurrent loopback HTTP.
`PoiSearchTest` verifies 32 Python fixture queries, separate missing/corrupt dictionaries,
HTTP partial/both failures, ranking, loopback Netty with 32 concurrent requests, and hashes.
This test server does not run Application.module, PostgreSQL, GTFS or background pollers.
Fixtures were generated by `experiments/local-poi/search.py search(q,50)` on the pinned SQLite.
Frontend tests cover both fields, stop priority, POI click, lack of refinement arrow,
editing, stale responses and existing address/stop scenarios. No browser UX claim is made.

## Postal subtitles, 10 November 2026

No SQLite schema/generator change or rebuild: Overture addresses already exist in
features.raw_json. Selected BDOT source records have no postal-address attributes.
`PoiAddress` reads only features attached to the current poi_id, with a prepared
query on the existing features_poi index. It never reads PRG or borrows an address
from another same-brand place. Only the returned candidates are enriched (max 50),
not the entire catalog in RAM. All source payloads and per-source licenses stay intact.

One unambiguous freeform line plus source locality and a terminal building-number
pattern is classified full; a nonempty line lacking these is partial. Locality alone
is counted as no postal address. Multiple normalized-distinct lines or conflicting
localities suppress the address line until reviewed; they do not select a building
arbitrarily. Freeform is displayed as supplied, not parsed into an invented street.
Fallback gmina names are administrative context, not inferred village addresses.

Visible coverage: full 207, partial 17, no usable postal line 182 (total 406).
Galeria Orkana: Orkana 6, Lublin; Galeria Mozaika: Orkana 4, Lublin;
Ball Packing Europe: Lublin only. Of two Perła sites, only the source-attached
Kunickiego site gets Władysława Kunickiego 106; the other stays Lublin.
Frontend already renders the API subtitle; both fields are tested against postal text.
No CSS, ranking, stop search, coordinate, routing or source-data changes.
Previous coordinate-subtitle descriptions and timing figures above are historical.

## Industrial address curation

The standard offline generator now embeds `address-overrides.json` in an independent
SQLite table. PoiAddress checks for this optional table and uses only confirmed rows,
then falls back to existing Overture raw addresses/locality. No API field, ranking,
coordinate, frontend or routing changes. Every override carries stable POI ID,
source IDs, identity/coordinate guards, source URL, checked date and confidence.
Source raw_json and licenses are preserved verbatim. No runtime external API calls.
Current industry coverage after 26 additions: 44 full / 2 partial / 28 without address
line, across the same 74 physical places. No extra POI is created from a second address.
Detailed accepted and pending decisions: experiments/local-poi/INDUSTRY_ADDRESS_DECISIONS.md.
