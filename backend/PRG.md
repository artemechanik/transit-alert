# Read-only PRG address search

Новий endpoint: GET /addresses/search?q=lipowa&limit=10.
Два поля планувальника (`frontend/js/planner-inputs.js`) використовують цей endpoint
з limit=4 замість MapTiler Geocoding. Пошук зупинок на табло та у звітах не змінювався.
MapTiler залишається джерелом картографічних ресурсів.

## Налаштування

PRG_SQLITE_PATH — шлях до вже готової SQLite. Для звичайного запуску можна задати:

```bash
export PRG_SQLITE_PATH=/home/artem/transit-alert/experiments/local-geocoder/data/addresses.sqlite
```

Без змінної сервіс шукає experiments/local-geocoder/data/addresses.sqlite від кореня репозиторію
або ../experiments/local-geocoder/data/addresses.sqlite від backend/.
Для іншого розташування/розгортання задайте абсолютний шлях явно.
База не входить до Git. Автоматичних імпорту, побудови індексу, завантаження чи міграції немає.
Шлях зчитується під час створення сервісу; сама база відкривається лише під час непорожнього пошуку.

Сервіс не використовує PostgreSQL, Exposed чи Python HTTP.
Кожен пошук відкриває окреме SQLite-з'єднання mode=ro + query_only=ON і закриває його разом
із statements/result sets. Одночасно виконується максимум 4 пошуки;
очікування дозволу coroutine-сумісне, блокувальний JDBC працює на Dispatchers.IO.
Ліміт задано `Semaphore(4)` на один екземпляр сервісу: решта запитів очікують,
а не отримують автоматичну відмову. Це не обмеження на 4 користувачів чи 4 запити/с.
SQL-бюджет починається після отримання дозволу й не включає очікування черги.
Перед масштабуванням достатність ліміту потрібно виміряти; завдання — у [TODO.md](../TODO.md).
SQLite progress handler обмежує виконання пошуку приблизно 2 секундами.
Окремого постійного процесу або фонового оновлення PRG немає.

## Контракт

200: query, results[], warning.
Результат містить type (street/address), id, source_id, display_name, locality, simc, terc,
street, house_number, lat, lon, match_rank, ulic, coordinate_kind, origin, representative_method.
Для street номер порожній, координати репрезентативні. Пропуски warning/representative_method серіалізуються як null.

Порожній q → 200 із порожнім списком; некоректний q/limit → 400.
Межі як у прототипі: максимум 200 символів і 12 слів, limit додатний, максимум 50.
Повторення параметра та невідомі параметри відхиляються.
Відсутня/пошкоджена/несумісна SQLite або перевищення SQL-часу → 503.
Інші API продовжують працювати; адресний маршрут не виконує перевірок/міграцій SQLite під час запуску backend.

Збережено нормалізацію польських літер, ul./al./pl., обробку номера/квартири,
вулиці з числом у назві, prefix/trigram пошук та весь ORDER BY Python-прототипу.
Без номера спочатку вулиці; за потреби список доповнюють безвуличні адреси.
З номером — адресні точки. Зміни ранжування/GPS/радіуса маршрутизації не додавалися.

## Підключення планувальника

Запити до `/stops/search` і `/addresses/search` виконуються паралельно через `apiFetch`.
Зупинки показуються першими, потім до чотирьох PRG-результатів без пересортування.
street → назва вулиці, address → вулиця/населений пункт + номер; населений пункт —
у другому рядку. Основний клік зберігає `{name, lat, lon}`; ↖ лише підставляє
назву з пробілом, очищує поточний вибір і залишає фокус для дописування.
Пошук вулиці без номера використовує репрезентативну точку, не адресу будинку.

Редагування скидає вибрані координати. Скасування/версія запиту захищають від
застарілих відповідей після набору, очищення, вибору, swap/GPS та закриття списку.
Адресний HTTP-таймаут — 5 с. Відмова PRG не приховує зупинки; автоматичного
fallback на MapTiler чи інший зовнішній геокодер немає.
HTTP 400 адресного запиту трактується як відсутність адресних підказок:
запит може бути валідним для зупинок, але не для адрес (наприклад, лише номер).
Дизайн карток, CSS та транспортна маршрутизація не змінені.

Історія, як і раніше, зберігає короткий name і прибирає дублікати за ним:
однакові короткі адреси різних місцевостей можуть зливатися в історії.
Радіус пошуку зупинок біля координат у маршрутизаторі залишається 800 м по прямій.
Ширше PRG-покриття не гарантує знайдений маршрут або пішохідну доступність.

## Перевірки

З backend/:

```bash
./gradlew test
./gradlew test --tests '*PrgAddressSearchTest'
```

Фікстури prg-query-fixtures.json містять повні відповіді Python-прототипу для всіх 58 сценаріїв:
40 початкових адресних (limit=10) + 18 street-сценаріїв (limit=50).
Їх отримано безпосередньо функцією geocoder.search над наявною SQLite,
а не вручну за першими картками старого звіту.
Еталонний SHA256 бази:
5b8ec52103d46b87b0dc36efbf1aa7920d07eb7677a15c21a6e10735fe630237

Тест підіймає справжній Netty лише на 127.0.0.1 із вільним портом,
порівнює всі поля/порядок/координати 58 відповідей, виконує 32 конкурентні HTTP-запити,
перевіряє незмінність SHA256 і зупиняє сервер у finally.
Application.module, PostgreSQL, GTFS та GPS-поллери не запускаються.
Окремо перевіряються 400/порожній q/limit, 32 конкурентні запити testApplication,
503 для відсутнього й пошкодженого файлу, доступність /status та відновлення після появи SQLite.
Ресурси тестових відмов створюються лише в тимчасовому каталозі.

Тести з реальною PRG-базою пропускаються (JUnit assumption), якщо локального файлу немає.
Для повного прогону задайте PRG_SQLITE_PATH на цей самий зріз; нові дані потребуватимуть
свідомого оновлення Python-фікстур. Тести не перебудовують і не змінюють довідник.

Робочий сервер під час реалізації не перезапускався.
Новий маршрут з'явиться в ньому після звичайного запуску оновленої збірки.

Frontend-перевірки: `node --experimental-vm-modules --test frontend/tests/*.test.mjs`.
`planner-modules.test.mjs` містить 14 сценаріїв для обох полів, контракту PRG,
вибору/↖, уточнення номера, GPS/swap, змішаних маршрутів і відмов/таймауту.
Перевірено також 58 реальних HTTP-відповідей Kotlin в окремому тестовому Netty.
Браузерний інструмент агента був недоступний, але 08.11.2026 власник сам
перевірив застосунок після перемикання на PRG: наразі зауважень немає.
За його суб'єктивною оцінкою пошук значно швидший за попередній.
Це не контрольований бенчмарк або підтвердження поведінки під майбутнім навантаженням.
Робочий сервер агент під час перемикання не перезапускав.

## Доповнення: локальні POI (10.11.2026)

`/addresses/search` тепер може повертати також `type=poi` через незалежний `PoiSearch`.
Порядок усередині PRG і його алгоритм не змінено; спільне ранжування застосовується
після пошуку. Опис вище про виключно PRG-видачу й порядок усіх чотирьох карток
стосується попередньої версії. Актуальний контракт, відмовостійкість, змінна
`POI_SQLITE_PATH` та перевірки — [POI.md](POI.md).
